# どんなプロジェクトに向いているか

パーツ組み換え設計は、**機能の一部を変更・交換するとき、ほかの機能をなるべく変更したくないプロジェクト**に向いている。

## 向いているケース

- **長期間保守するアプリケーション**：一部の機能を継続的に改善・作り直す。
- **処理方式を差し替えるシステム**：データ変換、計算方法、外部サービスとの接続処理などを交換する。
- **機能ごとに開発・検証するプロジェクト**：パーツの入出力契約を定め、既存のテストで交換後の動作を確認する。

共通する条件は、パーツごとの役割と外部との契約を比較的明確にできること。

## 向いていない、または効果が小さいケース

- **短い使い捨ての処理**：境界を設けるコストが、将来の組み換えによる利益を上回る。
- **共有状態や相互依存が全体に広がるシステム**：呼び出し関係を機能内へ閉じ込められず、変更の影響を局所化しにくい。
- **機能間の契約自体が頻繁に一斉変更されるプロジェクト**：内部を交換しても呼び出し元の変更を避けにくい。

これらの特徴が一部にあっても、その部分を一つのパーツに閉じ込められるなら適用できる場合がある。すべての箇所に一律で適用する必要はない。

## 適用前に確認すること

1. ある機能の内部を交換するとき、呼び出し元の変更を避けられるか。
2. 内部処理が別の機能から直接使われていないか。
3. 境界を細かくする管理コストより、組み換え時の負担削減が大きいか。

目的は細分化そのものではなく、**必要な範囲を、必要なコストで組み換えられること**にある。
